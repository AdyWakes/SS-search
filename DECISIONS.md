# Decisions log

Ambiguities resolved during the autonomous build, newest last. Each entry: what, why, how to revisit.

1. **Name: kept "shotfind".** `shotfind` is unused on crates.io and npm (checked 2026-11-05). It is short, says what it does, and is easy to type. Bundle identifier: `io.github.shotfind`.
2. **Workspace split.** All indexing/search logic lives in `crates/shotfind-core` (no Tauri dependency), so it can be tested on any CI runner without WebKit/GTK. `src-tauri` is a thin shell: commands, windows, hotkey, tray.
3. **ONNX Runtime is loaded dynamically (`ort` `load-dynamic`) and bundled as a Tauri resource.** `ort`'s default `download-binaries` fetches from cdn.pyke.io at build time, which was unreachable from the build sandbox and adds a third-party CDN to the supply chain. Instead `scripts/fetch-onnxruntime.mjs` downloads Microsoft's official release (v1.22.0) from GitHub, verifies a pinned SHA-256, and drops the shared library in `src-tauri/resources/onnxruntime/`. The app loads it by absolute path, which also avoids picking up the old `onnxruntime.dll` that ships in `C:\Windows\System32` on some Windows builds.
4. **`ort` pinned to `=2.0.0-rc.15`.** It is a release candidate (no 2.0 stable yet); pinning exactly protects against API churn between RCs. Its baseline C API level works with ONNX Runtime >= 1.17.
5. **HEIC/HEIF/AVIF not decoded in v0.1.** Decoding needs libheif (LGPL, native, painful to ship on Windows) or OS codecs (WIC on Windows needs the paid/optional HEVC extension). Files with these extensions are recognised but not indexed. Tracked as a "good first issue" (platform decoders: WIC on Windows, ImageIO on macOS).
6. **Indexing order: screenshots first, newest first.** People search for recent screenshots; this makes the app useful within the first minute of indexing.
7. **Crash safety model.** Each file's attempt counter is committed *before* processing and reset on success. On startup, files with >= 3 unfinished attempts are marked failed ("crashed repeatedly") so one poisoned file can't crash-loop the app. Panics inside engines are caught per file. All per-file results are written in one SQLite transaction (WAL mode).
8. **Skipped folders:** hidden dirs (`.*`), `node_modules`, recycle bins, `*.photoslibrary` / Lightroom `*.lrdata` (derived copies of photos, huge), app bundles, and the app's own data dir. Nested enabled folders (Pictures/Screenshots inside Pictures) are scanned once, as their own root.
9. **Defaults for skip rules:** min file 2 KB, max 40 MB, min side 64 px (icons), max 80 MP (decompression-bomb guard). All configurable in Settings.
10. **Thumbnails:** 384 px longest side, JPEG q78 (~15–30 KB each), sharded `thumbs/xx/<id>.jpg` in app data.
11. **Background priority:** coordinator and worker threads use `THREAD_MODE_BACKGROUND_BEGIN` on Windows (lowers CPU *and* I/O priority) and lowest priority elsewhere. Default workers = cores/4 clamped to 1..3.
12. **OCR models: PaddleOCR PP-OCRv4 (Chinese+English) det + rec, no angle classifier.** Covers Latin text, digits, punctuation and CJK. The rec model embeds its dictionary in ONNX metadata. Screenshots are upright, so boxes are axis-aligned and the cls model is skipped (saves ~10% time).
13. **OCR tuning (measured on synthetic 1080p chat UI, 13–15 px text):** detection at max 1280 px long side (960 broke 13 px text; 1600 cost +40% for no gain); recognition at the model's native 48 px height (32/40 garbled text), batch size 1 (padding made batches slower on CPU). Very tall/wide captures are tiled with 25% overlap; boxes touching inner tile edges are dropped and duplicates merged.
14. **Digit look-alike fixing.** Tokens that contain digits and otherwise only O/o/l/I/| (plus : . , - /) are mapped to digits ("4O4" -> "404", "l2:3O" -> "12:30"). Lone "O"/"l" are left alone.
15. **Indexing speed setting** (Gentle / Balanced / Fast = 1/4, 1/2, all-but-one CPU threads). Workers = budget/2, each with 2 ONNX threads (2 threads scaled ~1.8x vs 1 in benchmarks).
16. **Where models come from.** Hugging Face was unreachable from the build sandbox, so sources were picked for verifiability:
    - OCR: the `rapidocr_onnxruntime-1.4.4` wheel on PyPI (immutable files, SHA-256 published by PyPI) contains the official PP-OCRv4 ONNX exports. The app downloads the 14.9 MB wheel, verifies it, extracts only `det.onnx` and `rec.onnx`, verifies those too, and discards the rest. No code from the wheel is used.
    - CLIP: `Xenova/clip-vit-base-patch32` 8-bit quantized ONNX (vision ~89 MB, text ~64.5 MB) from Hugging Face. The text model hash came from the Hugging Face file page (via web search); the vision model hash could not be obtained here, so it is **not pinned yet**. The app refuses unpinned downloads: run `node scripts/pin-models.mjs` once with internet, review, commit. CI's `model-tests` job prints all upstream hashes (`--verify`) and warns while any is unpinned.
17. **Downloads:** HTTPS only, OS certificate store (works behind corporate TLS proxies), proxy from `HTTPS_PROXY`, resumable via HTTP Range, hashed while streaming, discarded on mismatch. A marker (`installed.json`) records verified hashes + sizes; startup checks sizes only (no re-hash of 150 MB per launch). Offline install: "Import models from folder" accepts the final or upstream file names and verifies hashes.
18. **CLIP preprocessing:** near-square images use the standard resize + centre crop; wide/tall images (most screenshots) are letterboxed on a mean-colour background so the whole screen is embedded instead of its middle third.
19. **CLIP tokenizer is reimplemented in Rust** (byte-level BPE, port of openai/CLIP `simple_tokenizer.py`) with OpenAI's merges file compiled in (MIT). Avoids the `tokenizers` crate (Oniguruma C build) and a tokenizer download. Verified against reference token ids. Not implemented: `ftfy` text fixing (irrelevant for short queries).
20. **Testing without the real CLIP model:** `tests/embed_plumbing.rs` builds tiny ONNX models by hand (protobuf writer in the test) with CLIP's input/output names and shapes, which covers loading, I/O wiring and normalisation. Real-CLIP ranking is checked by an ignored test that runs once the model is installed.
21. **Text search design.** FTS5 (`unicode61`, diacritics removed) over OCR text + a "searchable" file name (camelCase/underscores split). Each query word expands to vocabulary terms (from `fts5vocab`) that match exactly (1.0), by prefix for the last word as you type (0.9), as OCR look-alikes like UPl/UPI, C0de/Code, rn/m (0.9), or within an edit distance of 1 (words of 4–6 chars, 0.75) or 2 (7+ chars, 0.55, transpositions count as 1). Numbers never match fuzzily ("404" never matches "401"). Files with all the words come first; when they are few, files with some of the words are added. Score = mean per-word match quality (name matches x0.8), +0.15 if the whole query appears as a phrase.
22. **Combined ranking:** `score = text_score + 0.8 * semantic_score`, where semantic_score maps CLIP cosine 0.19..0.32 to 0..1 and only hits within 0.07 of the best (and >= 0.21 absolute) count. A full exact text match (1.0–1.15) beats a pure meaning match (<= 0.8); a strong meaning match beats weak fuzzy text. These constants live in `search::tuning` and **need calibration with the real CLIP model** (only fake embeddings were available here).
23. **Empty query = most recent images**, so opening the app shows your latest screenshots immediately.
24. **Raw query text goes to CLIP** (no "a photo of ..." prompt template); screenshots are not photos, and templates helped photos but not UI captures in published zero-shot results. Easy to revisit in `search.rs`.
25. **UI structure:** one main window (big search field, three quiet filters, thumbnail grid, preview overlay, settings page, first-run consent) and one frameless quick-search window for the hotkey. Same React bundle, `?view=bar` selects the bar. No router, no state library.
26. **Visual design:** warm near-black / warm off-white neutrals following the OS light/dark setting, one accent (tangerine `#ff6b2c`, darker `#e4500e` on light for contrast) used only for focus, selection, highlights and the primary button. System UI fonts (Segoe UI Variable on Windows, SF on macOS) for a native, fast feel; 24 px search text; secondary text never below 12.5 px. No cards inside cards: tiles are bare thumbnails with a caption. No frontend-design skill was available in this environment, so this follows the brief directly.
27. **Window behaviour:** closing the main window hides it to the tray (indexing and the hotkey keep working); Quit is in the tray menu. The quick bar hides on blur/Esc and opens on the monitor it was last on, 22% from the top. Launch with `--hidden` to start in the tray (for autostart).
28. **The webview can only refer to files by index id.** `open`, `reveal`, `copy image`, full-size preview and thumbnails all resolve the path from the database in Rust. Capabilities grant no fs/shell/http access; the only plugin permission beyond core is the folder picker. The `thumb://` protocol serves cached thumbnails and (read-only) originals of indexed ids only.
29. **Index location:** `app_local_data_dir` (Windows: `%LOCALAPPDATA%\io.github.shotfind`), not Roaming, so a large index never syncs with roaming profiles.
30. **OCR rows:** boxes on the same row are joined with a space only when close (gap < 2.5x line height); far-apart boxes (sidebar vs. chat) become separate lines. Snippets in the grid are trimmed to start near the first match.
31. **Release workflow** builds Windows x64 (MSI + NSIS .exe), macOS arm64 + x64 (.dmg) and Linux x64 (.AppImage + .deb) with `tauri-action` into a **draft** release on `v*` tags. A preflight job fails the release if any model hash is unpinned (so a release can't ship a refused download). Builds are unsigned; README explains the SmartScreen/Gatekeeper steps.
